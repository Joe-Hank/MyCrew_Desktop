# 0002. 项目"指令"纯结构化入 DB，不再生成 YAML

## Status

Accepted

## Context

MyCrew v2 的项目指令管理采用了"生成 YAML 文件"的方式：前端通过表单收集用户输入，后端将其渲染为 YAML 格式的指令文件，再由 CrewAI 框架读取并执行。

这一方案在实践中暴露了多个问题：

1. **双重数据源**：项目配置同时存在于数据库（元信息）和 YAML 文件（指令详情）中，两者可能不一致
2. **原子性缺失**：修改一个任务的依赖关系需要同时更新数据库记录和重新生成 YAML，缺乏事务保证
3. **查询困难**：无法直接通过 SQL 查询"所有使用了某个 Agent 的任务"，必须解析 YAML 文件
4. **版本控制复杂**：YAML 文件的变更历史难以与数据库变更对齐

v3 的设计目标是让 SQLite 成为唯一数据源。项目和任务的所有配置信息——包括依赖关系（`deps`）、输出模式（`output_schema`）、上下文变量等——都以结构化记录存储在数据库表中。对于复杂的嵌套数据（如任务依赖图），使用 JSON 字段存储。

考虑过的替代方案：

- **继续使用 YAML + DB 双源**：被否决，原因如上
- **纯 YAML，不用 DB**：不适合 GUI 应用的实时编辑和查询需求
- **TOML 代替 YAML**：换格式不解决根本问题

## Decision

所有项目和任务数据以结构化记录存储在 SQLite 数据库中，不再生成任何 YAML 指令文件。

具体数据模型设计：

1. **`projects` 表**：存储项目级配置（名称、描述、根路径、权限开关、LLM 默认选择等）
2. **`tasks` 表**：存储任务定义（描述、期望输出、所属 Agent、依赖任务列表等）
3. **JSON 字段**：对于 `deps`（依赖列表）、`output_schema`（输出模式定义）等半结构化数据，使用 SQLite 的 JSON 字段存储
4. **执行时转换**：当 CrewAI 需要执行时，由 `workflow_svc` 从数据库读取结构化数据并在内存中构建 Crew 对象，无需中间文件

## Consequences

**正面影响：**

- 单一数据源（Single Source of Truth）：所有项目配置集中在 SQLite 中，消除数据不一致风险
- 支持 SQL 查询：可以轻松查询跨项目的 Agent 使用情况、任务依赖图等
- 原子更新：利用 SQLite 事务保证配置变更的原子性
- 前端实时编辑体验更好：修改即保存，无需"生成文件"步骤

**负面影响：**

- 缺少人类可读的导出格式：用户无法直接在文件系统中浏览项目配置
- 调试时需要使用 SQLite 客户端或应用内调试工具查看数据

**中性影响：**

- 未来可以按需添加 YAML/JSON 导出功能，作为只读快照而非数据源
- 数据库迁移（schema migration）需要纳入版本发布流程
