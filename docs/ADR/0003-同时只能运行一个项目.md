# 0003. 同时只能运行一个项目

## Status

Accepted

## Context

在设计 MyCrew v3 的项目执行模型时，我们面临一个关键决策：是否允许用户同时运行多个项目？

支持并发运行多项目会带来显著的技术复杂度：

1. **调度器复杂度**：`workflow_svc` 需要管理多个独立的任务执行图，处理资源竞争、优先级调度等问题
2. **资源管理**：多个项目同时调用 LLM API 会产生并发限流问题（rate limiting），需要实现全局请求队列和令牌桶
3. **UI 状态管理**：前端需要同时展示多个项目的运行状态、日志流、交互请求，增加大量 UI 复杂度
4. **内存压力**：每个运行中的项目都需要维护 Agent 实例、上下文缓存、WebSocket 连接等，内存占用线性增长
5. **交互冲突**：当两个项目的 Agent 同时请求人工输入（Human Input）时，用户体验会非常混乱

作为一个个人桌面应用（非多用户 SaaS），并发运行多项目的实际需求较弱。用户的典型工作流是：聚焦一个项目 → 运行 → 查看结果 → 切换到下一个。

考虑过的方案：

- **方案 A：完全并发**——技术成本高，收益有限
- **方案 B：队列模式**——项目排队依次执行，降低复杂度但用户感知延迟
- **方案 C：单项目运行（本决策）**——最简单，符合当前使用场景

## Decision

在同一时刻，只允许一个项目处于 RUNNING 状态。

实现方式：

1. **`projects.is_running` 布尔字段**：标记当前正在运行的项目
2. **应用层保证**：`workflow_svc` 在启动新项目前检查是否有其他项目正在运行，如果有则拒绝启动并提示用户
3. **不在 schema 层硬约束**：数据库层面不添加排他约束（如 partial unique index），而是在服务层通过逻辑检查实现。这为未来放宽限制保留了灵活性
4. **暂停/恢复机制**：用户可以暂停当前项目（PAUSED 状态），然后启动另一个项目。暂停的项目保留执行上下文，稍后可恢复

## Consequences

**正面影响：**

- 调度器实现大幅简化：无需处理资源竞争、优先级队列等并发逻辑
- UI 状态管理清晰：运行面板始终展示唯一活跃项目的状态
- 资源使用可预测：LLM API 调用、内存占用等都在单项目范围内，易于估算和控制
- 人机交互无歧义：所有 `prompt.request` 都来自同一个项目的 Agent

**负面影响：**

- 用户如需同时推进两个项目，必须手动暂停当前项目再切换
- 长时间运行的项目会"独占"应用，可能影响其他项目的进度

**中性影响：**

- 未来版本可以通过修改 `workflow_svc` 的检查逻辑放宽为"最多 N 个并发"，schema 层面无需变更
- 暂停/恢复机制本身具有独立价值，即使未来支持并发也需要保留
