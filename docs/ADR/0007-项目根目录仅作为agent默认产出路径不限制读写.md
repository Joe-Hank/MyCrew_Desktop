# 0007. 项目根目录仅作为 Agent 默认产出路径，不限制读写

## Status

Accepted

## Context

MyCrew v3 的每个项目都有一个 `root_path`（项目根目录），Agent 在执行任务时可能需要读写文件。我们需要决定对 Agent 的文件系统访问权限采取何种策略。

### 安全 vs 实用性的权衡

在多用户 SaaS 或企业环境中，严格的路径沙箱化（sandboxing）是必要的安全措施——防止一个用户的 Agent 访问另一个用户的文件。但 MyCrew v3 是**个人桌面应用**，运行在用户自己的机器上，只有一个用户。

在这种场景下，限制 Agent 只能在 `root_path` 内读写会严重降低其实用性：

1. **跨目录操作**：Agent 可能需要读取 `~/Documents` 中的参考资料，然后将结果写入 `~/Projects` 中的另一个项目
2. **系统工具集成**：调用 Git、npm 等工具时，工作目录不一定在 `root_path` 内
3. **临时文件**：某些 Tool 需要在系统临时目录（`/tmp`、`%TEMP%`）中创建中间文件

考虑过的方案：

### 方案 A：严格沙箱——所有读写限制在 root_path 内
- 优点：最高安全性
- 缺点：对个人桌面应用过于严格，大量合理操作被阻断

### 方案 B：白名单路径——用户配置允许访问的路径列表
- 优点：灵活性与安全性的折中
- 缺点：配置复杂，用户需要预先知道 Agent 会访问哪些路径

### 方案 C：root_path 仅作默认路径，不限制访问（本决策）
- 优点：最大灵活性，适合个人使用场景
- 缺点：无路径级别的访问控制

## Decision

`projects.root_path` 作为 Agent 的默认输出目录（当 Agent 或 Tool 需要写文件但未指定路径时，使用 `root_path` 作为基础路径），但不对 Agent 的文件系统读写施加路径限制。

### 权限控制方式

通过项目级别的 9 个布尔权限开关提供粗粒度的能力控制：

| 权限开关 | 说明 |
|----------|------|
| allow_file_read | 允许读取文件 |
| allow_file_write | 允许写入文件 |
| allow_network | 允许网络请求 |
| allow_code_exec | 允许执行代码 |
| allow_shell | 允许执行 Shell 命令 |
| allow_browser | 允许使用浏览器工具 |
| allow_db_access | 允许访问数据库 |
| allow_human_input | 允许请求人工输入 |
| allow_delegation | 允许 Agent 间委派任务 |

### 实现细节

1. **默认路径注入**：`workflow_svc` 在构建 Crew 时，将 `root_path` 作为环境变量注入 Agent 上下文
2. **权限检查**：Tool 执行前检查对应的权限开关，如 `FileWriteTool` 检查 `allow_file_write`
3. **审计日志**：所有文件操作记录在 `task_logs` 表中，包含完整路径，便于事后审查

## Consequences

**正面影响：**

- 最大灵活性：Agent 可以自由访问用户文件系统中的任何资源，与手动操作等价
- 配置简单：用户无需维护复杂的路径白名单
- 适合个人使用场景：单用户桌面应用不需要用户间的隔离

**负面影响：**

- 无路径级别的沙箱化：如果 Agent 的 Tool 实现有 bug 或被恶意提示注入（prompt injection），理论上可以读写任意文件
- 不适合直接扩展到多用户场景：如果未来 MyCrew 需要支持多用户，此决策需要重新审视

**中性影响：**

- 9 个权限开关提供了"能力级别"的粗粒度控制，虽然不限制路径，但可以完全禁止文件操作
- 审计日志提供事后追溯能力，弥补了缺乏事前控制的不足
- plan.md §11.5 中记录了未来加固路径：可在特定场景下引入可选的路径沙箱
